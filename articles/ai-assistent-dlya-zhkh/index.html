AI-ассистент для ЖКХ: как превратить обращение жителя в готовую заявку - с контролем персональных данных

Andrey Semenov Hypermarket Director | Operational Excellence | AI Business Transformation

Когда жителю нужно сообщить о неисправности, он обычно звонит диспетчеру. Диспетчер выслушивает проблему, уточняет адрес и контактные данные, записывает информацию и передаёт её мастеру.

На практике в таком процессе есть несколько слабых мест: часть деталей теряется при передаче, заявки фиксируются не всегда одинаково, диспетчер тратит время на уточнения, а жителю приходится объяснять одну и ту же ситуацию несколько раз.

Для управляющей компании я разработал Telegram-бота, который принимает обращения на естественном русском языке, уточняет недостающую информацию и формирует структурированную заявку для диспетчера.

При этом проектировалась не просто диалоговая оболочка над языковой моделью. Важной частью задачи стала архитектура обработки персональных данных и разделение ответственности между AI и программной логикой.

Что получает бизнес

Житель может написать обычным сообщением:

«Перестала работать газовая колонка. Нужен мастер завтра после пяти».

Бот ведёт диалог, собирает необходимые сведения и формирует заявку. В результате диспетчер получает структурированное уведомление, в котором есть:

  • ФИО и телефон жителя;
  • адрес;
  • описание неисправности;
  • категория обращения;
  • дата и время визита;
  • информация о срочности.

Жителю не нужно заполнять длинную анкету или выбирать категорию из большого списка. Бот сам определяет, каких данных не хватает, и задаёт уточняющие вопросы.

По результатам тестирования заявка собирается примерно за 4-6 сообщений.

Главная идея: использовать AI там, где он действительно полезен - для понимания свободного текста и ведения диалога, - а критически важные операции выполнять предсказуемым программным кодом.

Как устроена архитектура

В основе решения - Python, Telegram Bot API и GigaChat API.

Поток обработки выглядит следующим образом:

  1. Житель отправляет сообщение в Telegram.
  2. Бот передаёт контекст диалога языковой модели.
  3. GigaChat извлекает сведения из сообщения и определяет, какие поля заявки ещё не заполнены.
  4. Программная логика проверяет и обрабатывает полученные данные.
  5. После сбора необходимой информации формируется заявка.
  6. Данные сохраняются в SQLite, а диспетчер получает уведомление в Telegram.

Здесь есть несколько принципиальных архитектурных решений.

1. Модель понимает язык, код отвечает за точность

Я не стал доверять языковой модели все решения без дополнительной проверки.

Например, житель может написать: «Пришлите мастера завтра к пяти». Для человека смысл очевиден, но для системы важно превратить относительную дату в конкретное значение.

В запрос модели передаётся текущая дата. Она должна вернуть абсолютную дату визита, а программная логика проверяет и обрабатывает временные значения. Срочность также определяется по заданным правилам, а не только по формулировке модели.

Тот же принцип применяется к другим полям заявки.

Архитектурное правило: всё, что можно надёжно вычислить обычным кодом, не нужно поручать языковой модели.

AI отвечает за понимание естественного языка. Код - за проверки, даты, правила и выполнение операций.

2. Структурированный ответ модели - это не гарантия корректных данных

Для дальнейшей обработки мне было важно получать от GigaChat структурированный ответ в формате JSON.

Но в ходе разработки выяснилось, что заявленный формат ответа не всегда поддерживается так, как ожидает разработчик. Даже успешный HTTP-ответ не гарантирует, что модель вернёт данные в нужной структуре.

Поэтому я реализовал несколько уровней защиты:

  • чёткий контракт формата ответа в системном промпте;
  • обработчик, который извлекает JSON из ответа;
  • обработку Markdown-обрамления и двойного кодирования;
  • повторные запросы при некорректном формате;
  • безопасный сценарий, если получить корректный ответ не удалось.

Это важный момент при разработке AI-интеграций: нельзя считать ответ модели корректным только потому, что API вернул HTTP 200.

3. Диалог проектировался как бизнес-процесс

Отдельная задача - сделать так, чтобы бот не просто задавал вопросы, а последовательно собирал заявку.

Например, не стоит благодарить человека по имени, если он ещё не представился. Не нужно одновременно задавать несколько вопросов, если пользователь должен последовательно сообщить разные сведения.

Поэтому я зафиксировал порядок сбора данных и правила переходов между этапами диалога.

Бот задаёт по одному вопросу за раз, не обращается к жителю по имени до знакомства и не должен повторно запрашивать уже полученную информацию без необходимости.

Это кажется мелочью, но именно такие детали определяют, будет ли человек пользоваться ботом или вернётся к обычному звонку диспетчеру.

4. Персональные данные - часть архитектуры, а не дополнительная функция

В заявках ЖКХ могут содержаться ФИО, телефоны и адреса жителей. Поэтому защиту данных я учитывал уже при проектировании решения.

В реализации предусмотрены:

  • получение согласия на обработку данных при первом запуске;
  • доступ к тексту политики обработки персональных данных через команду /policy;
  • шифрование персональных данных перед сохранением в SQLite с использованием Fernet;
  • маскирование телефонных номеров в логах;
  • команда /delete для запуска удаления данных пользователя;
  • автоматическое удаление заявок по истечении установленного срока хранения - 90 дней.

Fernet использует AES-128 в режиме CBC для шифрования и HMAC для проверки целостности данных.

Важно понимать: шифрование базы не заменяет защиту всей инфраструктуры. Необходимо также контролировать доступ к ключам, резервные копии, журналы, каналы передачи данных и настройки сервера.

В проекте предусмотрены технические механизмы, которые помогают организовать обработку персональных данных. Их наличие само по себе не является юридическим заключением о соответствии всей системы требованиям 152-ФЗ: это определяется с учётом конкретной модели обработки и условий эксплуатации.

Подробнее о том, какой путь проходят данные пользователя через цепочку сервисов - от мессенджера до внешней нейросети, - я разобрал в статье «Куда уходит сообщение клиента, когда он общается с AI-ботом?». Это вторая часть рубрики «Право и безопасность».

Инженерные сложности, которые пришлось решить

В процессе разработки я столкнулся с несколькими проблемами, характерными для интеграции российских AI-сервисов.

TLS и сертификаты. Первый запрос к GigaChat завершался ошибкой CERTIFICATE_VERIFY_FAILED. Причиной оказалось отсутствие нужных корневых сертификатов в стандартном хранилище Python. Я настроил отдельный bundle сертификатов и передал его HTTP-клиенту.

Авторизация API. Ключ из кабинета разработчика нельзя было напрямую использовать как Bearer-токен. Потребовалась двухэтапная OAuth-авторизация: получение временного access token и последующее использование его при обращении к API. Чтобы не запрашивать токен при каждом сообщении, реализовано его кэширование и обновление с запасом по времени.

Нестабильность ответов модели. Даже при подробном системном промпте модель могла ошибаться в отдельных полях, путать сведения профиля Telegram с ФИО пользователя или нарушать порядок вопросов. Эти сценарии пришлось выявлять на реальных транскриптах диалогов и последовательно исправлять.

Промпт прошёл семь итераций, каждая из которых зафиксирована отдельным коммитом. Следующий шаг развития - автоматические end-to-end тесты на накопленных сценариях, чтобы изменения не возвращали уже исправленные ошибки.

Технологический стек

  • Python 3.12
  • aiogram 3 - Telegram-бот
  • GigaChat API - понимание естественного языка и извлечение информации
  • httpx - HTTP-клиент и интеграция с API
  • SQLite - хранение заявок
  • cryptography / Fernet - шифрование данных
  • Docker - контейнеризация приложения

Что можно развивать дальше

Текущая версия решает задачу приёма и структурирования обращений. Следующий этап - развитие рабочего процесса самой управляющей компании:

  • изменение статусов заявки диспетчером;
  • уведомление жителя о ходе выполнения;
  • прикрепление фотографий неисправностей;
  • история обращений по адресу;
  • аналитика по категориям, срокам и повторяющимся проблемам;
  • подготовка Docker Compose-конфигурации для развёртывания у заказчика.

Таким образом, бот может стать первым интерфейсом более широкой системы управления обращениями жителей.

Что этот проект показывает

Этот проект - пример того, почему разработка AI-бота для бизнеса не сводится к подключению языковой модели к Telegram.

Нужно спроектировать весь процесс: от первого сообщения пользователя до появления корректной заявки у сотрудника. Продумать обработку ошибок, формат данных, правила диалога, хранение информации и контроль доступа.

Я придерживаюсь простого принципа: AI должен упрощать взаимодействие человека с системой, но не должен становиться неконтролируемым источником бизнес-решений.

Именно поэтому в рабочих решениях важны не только возможности модели, но и архитектура вокруг неё.
